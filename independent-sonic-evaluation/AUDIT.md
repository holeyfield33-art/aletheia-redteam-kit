## 5. Does the exported score encode pitches?

**No.** [`pitch_encoding.json`](AUDIT_DATA/pitch_encoding.json) shows the following:

- The composer's download handler (`composer.html` line 59) serialises `JSON.stringify(score)`. The
  score has no note, pitch or frequency field.
- Pitches come from a fixed table that maps element kind to a MIDI note (`schema.NOTES` and
  `composer.html` line 31): function=60, validate=62, branch=64, loop=65, call=67, raise=69,
  return=71, hole=72, assign=74.
- `events.json` and `template.wav` are *derived* from the score. Every note depends only on the
  element kind. The waveform also uses one of 3 harmonic classes, chosen from a hash of the module
  path.

The **score is therefore a structured, non-musical JSON programming specification**: modules,
imports, signatures, and an AST-like body of branch, loop, assign, call, raise, return and hole
elements with exact Python expressions. Audio is a separate rendering of the element-kind sequence.
The project's own documentation says the same ("The score is authoritative. Audio alone does not
retain arbitrary names, expressions, nesting…").

## 6. Audit conclusions

- The prototype installs and runs as documented. The test-suite claim was reproduced: 90 tests
  pass, and the 2 previously skipped tests also pass on Linux.
- The template generator and the structural checker work on independently authored scores (see
  `FINAL_REPORT.md`, Claim A).
- The "musical" score is a nonmusical structured specification with audio attached afterwards. That
  determines the experimental design in `PROTOCOL.md`: condition B can carry exactly the same
  information as condition C without any musical vocabulary.
